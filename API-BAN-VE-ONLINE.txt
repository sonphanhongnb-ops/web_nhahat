không phải ví dụ minh hoạ.

================================================================================
 0. ĐỌC TRƯỚC KHI TÍCH HỢP — NHỮNG ĐIỂM PHẢI XỬ LÝ
================================================================================

Hệ thống hiện được thiết kế cho QUẦY VÉ nội bộ, chưa có cổng công khai cho
website. Sáu điểm dưới đây phải xử lý trước khi mở bán ra ngoài. Không phải lỗi
cần sửa gấp, nhưng bỏ qua thì website sẽ chạy sai.


(0.1) KHÔNG CÓ API CÔNG KHAI — MỌI ENDPOINT ĐỀU CẦN ĐĂNG NHẬP
      Chỉ /api/auth/* là công khai. Tất cả phần còn lại bắt buộc JWT.

      => Website phải gọi API từ MÁY CHỦ (server-side), dùng một TÀI KHOẢN DỊCH
         VỤ riêng. TUYỆT ĐỐI không đưa token xuống trình duyệt: token của hệ
         thống này mang quyền của nhân viên, lộ ra là mất quyền kiểm soát.

      Kiến trúc đúng:
         Trình duyệt  ->  Máy chủ website  ->  API hệ thống vé
                          (giữ token ở đây)

      Kiến trúc SAI:
         Trình duyệt  ->  API hệ thống vé      (token nằm trong JavaScript)


(0.2) TÀI KHOẢN DỊCH VỤ — ĐÃ TẠO SẴN
      Tài khoản riêng cho website đã được tạo, KHÔNG dùng admin:

         Tên đăng nhập : website_banve
         Vai trò       : "Website bán vé online"

      Mật khẩu được giao riêng, không ghi trong tài liệu này.

      HÌNH THỨC THANH TOÁN: CHỈ VNPAY.
      Tài khoản này bị khoá ở tầng máy chủ, chỉ thu được qua VNPay. Gửi lên bất
      kỳ hình thức nào khác — kể cả trộn VNPay với hình thức khác — đều bị từ
      chối HTTP 403. Xem mục 4.11.

      Đây là tài khoản DỊCH VỤ: được miễn yêu cầu gán quầy vé và phân ca hằng
      ngày (website chạy 24/7, không có quầy, không ai trực ca). Đổi lại, nó
      buộc phải có giới hạn hình thức thanh toán — cơ sở dữ liệu không cho tồn
      tại một tài khoản dịch vụ thu được bằng tiền mặt.

      Vai trò gồm đúng 5 quyền, không hơn:

         VE_BAN_VE_GHE         Xem sơ đồ ghế, giữ ghế, xuất vé
         KB_SUAT_DIEN_VIEW     Xem lịch diễn và bảng giá
         VE_DA_BAN_VIEW        Lấy vé + mã QR để gửi khách
         VE_KIEM_TRA           Trang tra cứu vé cho khách
         KB_HINH_THUC_TT_VIEW  Đọc id hình thức thanh toán (mục 4.11)

      KHÔNG có: hoàn vé, đổi vé, in lại vé, huỷ hoá đơn, báo cáo doanh thu,
      khai báo danh mục, quản lý người dùng, đọc/sửa cấu hình hệ thống.
      Gọi các endpoint đó sẽ nhận HTTP 403.

      Quản lý tài khoản (chạy trong thư mục db/):
         node seed-website-account.js --reset-pass   đổi mật khẩu
         node seed-website-account.js --sync-perms   đặt lại đúng bộ quyền
         node seed-website-account.js --remove       xoá tài khoản


(0.3) CORS ĐANG CHỈ CHO PHÉP localhost:5173
      File backend/.env:
         CORS_ORIGIN=http://localhost:5173

      Nếu gọi từ máy chủ website (đúng cách) thì CORS không liên quan.
      Chỉ khi nào gọi trực tiếp từ trình duyệt mới cần thêm tên miền vào đây —
      nhưng cách đó vi phạm mục (0.1), không nên làm.


(0.4) /showtimes/sellable CHỈ TRẢ VỀ ĐÚNG MỘT NGÀY
      Không truyền tham số thì mặc định là NGÀY HÔM NAY.
      Muốn hiện lịch diễn cả tuần/tháng, website phải gọi lặp từng ngày,
      hoặc dùng /seating/showtimes?fromDate=...&toDate=... (có phân trang).


(0.5) sale_open_at CHƯA ĐƯỢC HỆ THỐNG KIỂM TRA
      Bảng suất diễn có hai cột sale_open_at / sale_close_at, nhưng:
         - sale_close_at : CÓ kiểm tra, ở bước giữ ghế
         - sale_open_at  : KHÔNG kiểm tra ở bất kỳ đâu

      => Nếu website cần chặn "chưa tới giờ mở bán", phải TỰ kiểm tra
         sale_open_at ở phía website. Hệ thống sẽ không chặn giúp.


(0.6) VNPAY ĐÃ ĐƯỢC TÍCH HỢP SẴN — DÙNG MỤC 4B, KHÔNG TỰ LÀM
      Hệ thống vé đã tự lo trọn khâu thanh toán: dựng đường dẫn VNPay, nhận IPN,
      xuất vé. Website CHỈ cần gọi 2 endpoint (tạo đơn, tra trạng thái).

      => KHÔNG dùng mục 4.6 (giữ ghế) + 4.8 (xuất vé) cho bán online. Hai mục đó
         dành cho quầy vé. Tự ghép chúng với cổng thanh toán sẽ tạo lại đúng lỗ
         hổng "khách trả tiền mà không có vé" mà mục 4B đã bịt.

      Đọc thẳng MỤC 4B.


================================================================================
 1. THÔNG TIN CHUNG
================================================================================

Địa chỉ gốc:
    https://ticket-api-tamchuc.vercel.app/api     (đã chạy trên Internet)
    http://localhost:4000/api                     (máy phát triển)

Định dạng:
    - Gửi và nhận đều là JSON, mã hoá UTF-8
    - Header bắt buộc khi gửi dữ liệu:  Content-Type: application/json
    - Thời gian theo chuẩn ISO 8601 kèm múi giờ, ví dụ:
          "2026-07-24T15:19:40.057+00:00"
    - Tiền là số, đơn vị đồng, không có dấu phân cách:  350000
    - Mọi định danh (id) là UUID

Giới hạn tần suất:
    300 lượt gọi / 1 phút / 1 địa chỉ IP.
    Vượt ngưỡng trả về HTTP 429.

CẤU TRÚC PHẢN HỒI — mọi endpoint đều theo đúng khuôn này:

    Thành công:
        {
          "success": true,
          "data": { ... }
        }

    Thành công + phân trang:
        {
          "success": true,
          "data": [ ... ],
          "meta": { "page": 1, "pageSize": 20, "total": 57, "totalPages": 3 }
        }

    Thất bại:
        {
          "success": false,
          "message": "Mô tả lỗi bằng tiếng Việt, hiển thị được cho khách",
          "errors":  [ ... ],   (chỉ có khi lỗi kiểm tra dữ liệu)
          "details": { ... }    (chỉ có khi lỗi tranh chấp ghế)
        }

    LƯU Ý: dữ liệu thật luôn nằm trong trường "data", không nằm ở gốc.

MÃ TRẠNG THÁI HTTP:

    200  Thành công
    201  Đã tạo (chỉ ở bước xuất vé)
    400  Dữ liệu gửi lên sai       -> kèm mảng "errors", sửa dữ liệu rồi gửi lại
    401  Chưa đăng nhập / hết hạn  -> đăng nhập lại lấy token mới
    403  Không đủ quyền            -> tài khoản dịch vụ thiếu quyền, xem (0.2)
    404  Không tìm thấy
    409  Xung đột                  -> ghế bị người khác lấy, hoặc trả thiếu tiền
    429  Gọi quá nhiều             -> chờ rồi thử lại
    500  Lỗi máy chủ


================================================================================
 2. XÁC THỰC
================================================================================

Hệ thống dùng JWT. Sau khi đăng nhập, gắn token vào mọi lần gọi tiếp theo:

    Authorization: Bearer <token>

Token có hạn sử dụng. Khi nhận HTTP 401 kèm thông báo
"Chưa đăng nhập hoặc phiên đã hết hạn" thì đăng nhập lại để lấy token mới.

KHUYẾN NGHỊ: máy chủ website nên lưu token trong bộ nhớ và tự đăng nhập lại khi
gặp 401, thay vì đăng nhập lại ở mỗi lần gọi.


================================================================================
 3. LUỒNG ĐẶT VÉ ONLINE — SƠ ĐỒ 6 BƯỚC
================================================================================

  BƯỚC 1   Hiện lịch diễn
           GET /seating/showtimes/sellable?date=2026-07-24
                 |
  BƯỚC 2   Khách chọn suất -> vẽ sơ đồ ghế
           GET /seating/showtimes/{id}/seat-map
                 |
  BƯỚC 3   Khách chọn ghế -> hiện tổng tiền
           POST /seating/seats/preview
                 |
  BƯỚC 4   Khách bấm "Thanh toán" -> GIỮ GHẾ NGAY (5 phút)
           POST /seating/seats/hold        -> nhận hold_token
                 |
                 |  Chuyển khách sang cổng thanh toán (VNPay/Momo...)
                 |  Cổng báo về THÀNH CÔNG
                 |
  BƯỚC 5   Xuất vé
           POST /seating/seats/issue       -> gửi kèm hold_token
                 |
  BƯỚC 6   Lấy vé + mã QR, gửi email cho khách
           GET /sales/invoices/{id}/print-data


  NẾU KHÁCH HUỶ hoặc THANH TOÁN THẤT BẠI:
           POST /seating/seats/release     -> trả ghế lại ngay,
                                              đừng đợi hết 5 phút

  QUY TẮC QUAN TRỌNG:
    - Giữ ghế NGAY TRƯỚC khi chuyển sang thanh toán, không giữ sớm hơn
      (giữ sớm làm ghế bị khoá vô ích, khách khác không mua được)
    - hold_token phải được truyền nguyên vẹn từ bước 4 sang bước 5
    - Ghế chỉ được giữ 5 phút. Quá hạn, hệ thống tự nhả.

CÁCH VẼ SƠ ĐỒ:
    Khán đài chia thành nhiều KHU (blocks). Mỗi khu là một lưới ghế riêng, có
    toạ độ và GÓC XOAY riêng trên mặt bằng — vì khán đài hình quạt, các khu hai
    bên nghiêng về phía sân khấu.

    Vị trí một ghế trên mặt bằng:
        x = block.offset_x + seat.col_index
        y = block.offset_y + seat.row_index
    rồi xoay cả khu quanh gốc của nó theo block.rotation_deg
    (số dương = xoay theo chiều kim đồng hồ).

    Nhãn hiển thị cho khách: dùng full_label (ví dụ "A1", "H22").
    Nhãn này DUY NHẤT trong toàn khán đài, không cần ghép thêm tên khu.

sale_state — TRẠNG THÁI BÁN CỦA GHẾ (quyết định màu sắc trên sơ đồ):

    TRONG      Còn trống, chọn được
    DANG_GIU   Người khác đang giữ, KHÔNG chọn được (hiện màu xám)
    CUA_TOI    Chính phiên này đang giữ (hiện màu nổi bật)
    DA_BAN     Đã bán, KHÔNG chọn được
    HONG       Ghế hỏng/ngưng dùng, KHÔNG chọn được
    LOI_DI     Ô lối đi, không phải ghế — không vẽ, nhưng vẫn chiếm chỗ trên lưới

    Website chỉ được cho khách chọn ghế có sale_state = "TRONG".

GHI CHÚ:

      cho khớp với màn hình quầy.
    - pair_key: hai ghế cùng pair_key là GHẾ ĐÔI, phải bán kèm nhau.
      Nếu khán đài có ghế đôi, website phải tự động chọn cả cặp.

--------------------------------------------------------------------------------
 4B.1  VÌ SAO KHÔNG TỰ GHÉP CỔNG THANH TOÁN
--------------------------------------------------------------------------------

Cách làm tự nhiên mà SAI:

    website giữ ghế -> website thu tiền -> website gọi API xuất vé

Cách này để hở một khoảng chết: tiền đã trừ của khách nhưng lệnh xuất vé hỏng
(hết hạn giữ ghế, mất mạng, website sập giữa chừng). Khách mất tiền, không có vé,
và hệ thống vé KHÔNG HỀ BIẾT chuyện đó đã xảy ra.

Cách hệ thống đang làm:

    website tạo đơn -> khách trả tiền ở VNPay
                          |
                          v
              VNPay gọi thẳng IPN về MÁY CHỦ VÉ
                          |
                          v
                 máy chủ vé xuất vé ngay tại chỗ

Không có trung gian. Website sập giữa chừng cũng không mất đơn nào — vé vẫn được
xuất, khách vẫn nhận được.

 4B.2  SƠ ĐỒ LUỒNG
--------------------------------------------------------------------------------

  BƯỚC 1  Khách chọn suất, chọn ghế  (mục 4.2, 4.4, 4.5)
              |
  BƯỚC 2  Khách bấm "Thanh toán"

              -> hệ thống giữ ghế 15 phút, trả về pay_url

              |

              |

          GET /sales/invoices/{invoice_id}/print-data

    thanh địa chỉ mà VNPay chuyển về — khách sửa được URL đó.


--------------------------------------------------------------------------------
 4B.5  ĐỐI CHIẾU KHI IPN KHÔNG TỚI  (tuỳ chọn, là lưới an toàn)
--------------------------------------------------------------------------------
    POST /api/payments/vnpay/return
    Quyền: VE_BAN_VE_GHE

    IPN là đường quyết định, nhưng nó cần máy chủ vé MỞ RA INTERNET để VNPay gọi
    vào được. Nếu máy chủ nằm sau tường lửa hoặc chưa mở cổng, IPN không tới và
    đơn treo mãi ở CHO_THANH_TOAN dù khách đã trả tiền.

    Endpoint này là lối thoát: website chuyển NGUYÊN VẸN query string mà VNPay
    gắn vào Return URL, máy chủ tự kiểm chữ ký rồi chốt đơn.

GỬI LÊN — nguyên các tham số vnp_* nhận được, không sửa gì:
    {
      "vnp_Amount": "50000000",
      "vnp_BankCode": "NCB",
      "vnp_ResponseCode": "00",
      "vnp_TransactionStatus": "00",
      "vnp_TxnRef": "OL260721000003",
      "vnp_TransactionNo": "14312345",
      "vnp_SecureHash": "abc123...",
      ...
    }

NHẬN VỀ:
    {
      "success": true,
      "data": {
        "rsp_code": "00",
        "message": "Confirm Success",
        "order": { ... giống mục 4B.4 ... }
      }
    }

    Chạy CÙNG một hàm với IPN nên gọi bao nhiêu lần cũng không xuất vé hai lần.
    Chữ ký vẫn được kiểm đầy đủ — khách sửa tham số trên URL thì rsp_code = 97.

    KHUYẾN NGHỊ: gọi endpoint này ở trang kết quả, rồi mới gọi 4B.4. Như vậy
    đơn được chốt kể cả khi IPN chưa/không tới.


--------------------------------------------------------------------------------
 4B.6  KHI ĐÃ TRỪ TIỀN MÀ VÉ KHÔNG XUẤT ĐƯỢC  (status = LOI_XUAT_VE)
--------------------------------------------------------------------------------

Nguyên nhân gần như luôn là: khách trả tiền quá chậm, hết hạn giữ ghế, và ghế đã
bị người khác mua mất trong lúc đó.

Hệ thống KHÔNG im lặng bỏ qua: đơn được ghi rõ trạng thái LOI_XUAT_VE kèm
error_message, và khoản tiền vẫn có dấu vết đầy đủ (vnp_transaction_no, paid_at).

VIỆC WEBSITE PHẢI LÀM:
    - Hiện cho khách: "Thanh toán thành công nhưng chưa xuất được vé, bộ phận
      chăm sóc khách hàng sẽ liên hệ trong ít phút"
    - Báo ngay cho bộ phận vận hành (email/Slack/Zalo)
    - TUYỆT ĐỐI không hiện "Thanh toán thất bại" — khách đã mất tiền thật

VIỆC NHÂN VIÊN NHÀ HÁT LÀM:
    Thử xuất bù:
        POST /api/payments/vnpay/orders/{order_code}/retry-issue

    Ghế còn trống thì vé được xuất, đơn chuyển sang HOAN_TAT.
    Ghế đã bị người khác mua thì lệnh này báo lỗi rõ ràng — khi đó phải HOÀN TIỀN
    cho khách qua trang quản trị VNPay.

TÌM CÁC ĐƠN CẦN XỬ LÝ:
    GET /api/payments/vnpay/orders?status=LOI_XUAT_VE
    Quyền: VE_DA_BAN_VIEW

    Nên có người kiểm danh sách này mỗi ngày.


--------------------------------------------------------------------------------
 4B.7  IPN — WEBSITE KHÔNG ĐỘNG VÀO
--------------------------------------------------------------------------------
    GET /api/payments/vnpay/ipn
    CÔNG KHAI — không cần đăng nhập

    Chỉ máy chủ VNPay gọi endpoint này. Ghi ở đây để bên vận hành biết mà mở
    tường lửa, KHÔNG PHẢI để website gọi.

    Không có token vì máy chủ VNPay không có tài khoản trong hệ thống. Bảo vệ
    bằng CHỮ KÝ HMAC-SHA512: mọi tham số đều bị kiểm chữ ký trước khi tin. Gói
    tin không có chữ ký đúng bị trả về mã 97 và không đụng được vào đơn nào.

    ĐỊA CHỈ CẦN KHAI BÁO trong trang quản trị merchant VNPay:
        https://ticket-api-tamchuc.vercel.app/api/payments/vnpay/ipn

    Máy chủ vé phải truy cập được từ Internet thì IPN mới tới. Nếu không mở
    được, dùng lưới an toàn ở mục 4B.5.

 4B.9  CẤU HÌNH PHÍA MÁY CHỦ VÉ  (backend/.env)
--------------------------------------------------------------------------------

    VNPAY_TMN_CODE=          Mã website, lấy trong trang quản trị merchant VNPay
    VNPAY_HASH_SECRET=       Khoá bí mật — KHÔNG đưa cho website, không đưa lên git
    VNPAY_PAY_URL=           sandbox: https://sandbox.vnpayment.vn/paymentv2/vpcpay.html

    VNPAY_RETURN_URL=        Trang kết quả của WEBSITE.
                             PHẢI khai báo TRÙNG KHỚP trong trang quản trị VNPay.
    VNPAY_TIMEOUT_MINUTES=15 Thời gian khách được trả tiền, cũng là thời gian giữ ghế

    Để trống TMN_CODE/HASH_SECRET thì tính năng bán online tắt, bán vé tại quầy

    Nếu máy chủ chạy sau nginx hoặc cân bằng tải, đặt thêm TRUST_PROXY=1 để đọc
    đúng IP của khách. Không có nó thì VNPay nhận sai vnp_IpAddr và bộ giới hạn
    tần suất gộp mọi khách vào chung một mối.

 4B.10  VÍ DỤ MÃ NGUỒN  (Node.js, chạy ở MÁY CHỦ website)

// ---- Khách bấm "Thanh toán" ----
app.post('/dat-ve', async (req, res) => {
  const { showtimeId, seatIds, khach } = req.body;

  const don = await call('POST', '/payments/vnpay/orders', {
    showtime_id: showtimeId,
    seat_ids: seatIds,
    booker_name:  khach.ten,
    booker_phone: khach.dienThoai,
    booker_email: khach.email,
  });

  // Lưu order_code vào phiên để trang kết quả tra lại
  req.session.orderCode = don.order_code;

  // Chuyển khách sang VNPay
  res.redirect(don.pay_url);
});


// ---- VNPay chuyển khách về (VNPAY_RETURN_URL) ----
app.get('/thanh-toan/ket-qua', async (req, res) => {
  // Chốt đơn ngay, phòng khi IPN chưa/không tới.
  // Máy chủ tự kiểm chữ ký, nên không cần tin dữ liệu trên URL.
  await call('POST', '/payments/vnpay/return', req.query).catch(() => {});

  const don = await call('GET', `/payments/vnpay/orders/${req.query.vnp_TxnRef}`);

  if (don.status === 'HOAN_TAT') {
    const ve = await call('GET', `/sales/invoices/${don.invoice_id}/print-data`);
    await guiEmailVe(don.booker_email, ve.tickets);   // hàm của website bạn
    return res.render('thanh-cong', { don, ve: ve.tickets });
  }

  if (don.status === 'LOI_XUAT_VE') {
    // ĐÃ TRỪ TIỀN mà chưa có vé — báo vận hành, KHÔNG nói "thất bại" với khách
    await baoVanHanh(don);
    return res.render('cho-xu-ly', { don });
  }

  if (don.status === 'CHO_THANH_TOAN') {
    // IPN chưa về — trang tự tải lại sau vài giây
    return res.render('dang-xu-ly', { orderCode: don.code });
  }

  // THAT_BAI hoặc HET_HAN — không trừ tiền, mời khách đặt lại
  return res.render('that-bai', { lyDo: don.error_message });
});

 6. XỬ LÝ TRANH CHẤP GHẾ
================================================================================

Bán vé online có hai rủi ro thật, phải xử lý ngay từ đầu.


RỦI RO 1 — HẾT 5 PHÚT GIỮ GHẾ TRONG LÚC KHÁCH ĐANG TRẢ TIỀN
-----------------------------------------------------------
Cổng thanh toán có thể mất hơn 5 phút (khách nhập OTP chậm, ngân hàng chậm).
Khi đó lượt giữ ghế hết hạn, ghế bị người khác mua mất, mà tiền khách đã trừ.

CÁCH XỬ LÝ:

  a) Giữ ghế MUỘN NHẤT CÓ THỂ
     Chỉ gọi hold ngay trước khi chuyển sang cổng thanh toán, không giữ từ lúc
     khách mới rê chuột chọn ghế.

  b) Hiện đồng hồ đếm ngược cho khách
     Dựa vào expires_at. Còn dưới 60 giây thì cảnh báo rõ.

  c) Gia hạn lượt giữ khi cần
     Gọi lại POST /seating/seats/hold, truyền kèm hold_token CŨ và đúng danh sách
     ghế đó. Nếu chưa ai lấy mất, hệ thống gia hạn thêm 5 phút.

  d) BẮT BUỘC: có quy trình xử lý khi vé xuất thất bại sau khi đã thu tiền
     Nếu POST /seats/issue trả 409 mà tiền đã trừ, website PHẢI:
        - Ghi lại giao dịch vào một bảng "chờ xử lý" của website
        - Thông báo cho khách và bộ phận chăm sóc khách hàng
        - Hoàn tiền tự động, HOẶC để nhân viên nhà hát xử lý thủ công
     TUYỆT ĐỐI không im lặng bỏ qua — đó là mất tiền của khách.


RỦI RO 2 — CÙNG MỘT GHẾ BÁN CHO HAI NGƯỜI
------------------------------------------
Hệ thống đã có hai lớp chống trùng, website KHÔNG cần tự xử lý:

  Lớp mềm:  giữ ghế 5 phút, có khoá đồng thời ở cơ sở dữ liệu
  Lớp cứng: ràng buộc duy nhất trên bảng vé — dù có lỗi lập trình ở lớp trên
            thì cơ sở dữ liệu vẫn từ chối vé thứ hai cho cùng một ghế

Việc của website: bắt đúng lỗi HTTP 409 ở cả hai bước hold và issue, rồi tải lại
sơ đồ ghế cho khách chọn lại.

QUY TẮC VÀNG: KHÔNG BAO GIỜ tự suy đoán ghế còn trống dựa trên bộ nhớ đệm của
website. Luôn tải lại sơ đồ từ máy chủ sau mỗi lần lỗi 409.

 8. PHỤ LỤC — VÍ DỤ MÃ NGUỒN
================================================================================

Ví dụ Node.js, chạy ở MÁY CHỦ website (không phải trong trình duyệt).

------------------------------------------------------------------------
const API = process.env.TICKET_API;  // https://ticket-api-tamchuc.vercel.app/api
let token = null;

async function login() {
  const r = await fetch(API + '/auth/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      username: process.env.TICKET_USER,
      password: process.env.TICKET_PASS,
    }),
  });
  const j = await r.json();
  if (!j.success) throw new Error('Đăng nhập hệ thống vé thất bại');
  token = j.data.token;
}

// Tự đăng nhập lại khi token hết hạn
async function call(method, path, body) {
  if (!token) await login();

  const send = () => fetch(API + path, {
    method,
    headers: {
      'Content-Type': 'application/json',
      Authorization: 'Bearer ' + token,
    },
    ...(body ? { body: JSON.stringify(body) } : {}),
  });

  let res = await send();
  if (res.status === 401) {       // token hết hạn -> lấy token mới, gọi lại
    await login();
    res = await send();
  }

  const json = await res.json();
  if (!json.success) {
    const err = new Error(json.message);
    err.status = res.status;
    err.details = json.details;   // details.blocked: ghế nào bị chặn
    throw err;
  }
  return json.data;
}
